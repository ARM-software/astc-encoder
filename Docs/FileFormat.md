# The .astc and .astcm File Formats

The default file format for compressed textures generated by `astcenc`, as well
as from many other ASTC compressors, is the `.astc` format. This is a very
simple format consisting of a small header followed immediately by the binary
payload for a single image surface.

Header
======

The header is a fixed 16-byte structure, defined as storing only bytes to avoid
any endianness issues or incur any padding overhead.

```
struct astc_header
{
    uint8_t magic[4];
    uint8_t block_x;
    uint8_t block_y;
    uint8_t block_z;
    uint8_t dim_x[3];
    uint8_t dim_y[3];
    uint8_t dim_z[3];
};
```

Magic number
------------

The 4-byte magic number at the start of the file acts as a format identifier.

```
    magic[0] = 0x13;
    magic[1] = 0xAB;
    magic[2] = 0xA1;
    magic[3] = 0x5C;
```

Block size
----------

The `block_*` fields store the ASTC block dimensions in texels. For 2D images
the Z dimension must be set to 1.

Image dimensions
----------------

The `dim_*` fields store the image dimensions in texels.  For 2D images the
Z dimension must be set to 1.

Note that the image is not required to be an exact multiple of the compressed
block size; the compressed data may include padding that is discarded during
decompression.

Each dimension is a 24-bit unsigned value that is reconstructed from the stored
byte values as:

```
decoded_dim = dim[0] + (dim[1] << 8) + (dim[2] << 16);
```

Binary payload
==============

The binary payload is a byte stream that immediately follows the header. It
contains 16 bytes per compressed block. The number of compressed blocks is
determined from the header information.

The .astcm format
=================

The `.astcm` format stores the same encoded ASTC blocks in an order intended
to improve locality for subsequent lossless compression. It supports 2D
images and 2D block footprints, including non-square footprints. It changes
neither the encoded blocks nor the decoded image quality.

The header has the same 16-byte layout as `.astc`, with the four magic bytes
replaced by the ASCII bytes `ASCM` (`0x41, 0x53, 0x43, 0x4D`). Both `block_z`
and `dim_z` must be one. Image dimensions must be nonzero and fit in 24 bits.
As with `.astc`, the color profile is supplied separately by the application.

The block grid is divided into bricks of 8 by 8 ASTC blocks. Bricks are stored
in raster order, with X changing fastest. Blocks inside each brick are stored
in Morton order, using the even bits of the Morton index for the local X
coordinate and the odd bits for the local Y coordinate:

```
for brick_y in range(0, blocks_y, 8):
    for brick_x in range(0, blocks_x, 8):
        for morton in range(64):
            x = brick_x + sum(((morton >> (2 * i)) & 1) << i for i in range(3))
            y = brick_y + sum(((morton >> (2 * i + 1)) & 1) << i for i in range(3))
            if x < blocks_x and y < blocks_y:
                write_block(x, y)
```

Blocks outside the image's block grid are skipped, so edge bricks add no
padding. The payload size is exactly `ceil(dim_x / block_x) * ceil(dim_y /
block_y) * 16` bytes. Each block retains its original byte order.

The codec API continues to use raster-ordered blocks. The CLI loader restores
raster order, and the CLI writer applies the Morton permutation when saving.
